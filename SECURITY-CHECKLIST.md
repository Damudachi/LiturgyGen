## 2. A door in front of the app

**LiturgyGen has a login, and it writes to a database.** Section 2 says that is itself the access layer, so the rows below record how it is built rather than which gate was bolted in front of it.

**Which option:** **A login of my own, built on Supabase Auth.** The announcement opens section 2 with "Some of you built a login, with Firebase or Supabase or your own sessions. If you did, that is your access layer" — this is that. It replaced an HTTP Basic Authentication gate, which was the right size of answer while LiturgyGen served one office and stopped being one the moment a second parish could sign up: a single shared password cannot say **which** parish is asking, and every query now has to know.
I do not have a domain in my own Cloudflare account, and the announcement is explicit that Access cannot carry a policy on a `trycloudflare.com` or `workers.dev` hostname. A login built on Supabase needs no domain of its own, works on any host, and is what is running on grading morning.
One thing the move cost, written down because it is the kind of detail that is easy to leave out: the gate guards `/api` and **only** `/api`. Registered above `express.static` it served a signed-out browser a JSON error instead of the page that draws the sign-in form, so nobody could ever sign in. The built client is therefore public — it is the same bundle for every parish and holds no data; all the scoping is behind `/api`.

| # | Item | Answer | Evidence |
| - | --- | --- | --- |
| 2.1 | An access layer is in place | **Yes** | `server/src/middleware/requireAuth.js`, registered in `src/app.js` **before every `/api` route**. It verifies the Supabase access token and resolves the caller to a parish; a request with no token, a forged token or the old `Basic` header all get **401**, verified by driving the middleware directly against the live project. A failure to *check* returns 503 and never `next()` — the one place the app fails closed. |
| 2.2 | The gate covers every route | **Yes, with three deliberate exceptions** | `/healthz`, `/readyz` and `GET /` are registered above the gate. `GET /` is a landing page: a fixed string of HTML built in `src/views/pages.js`, with no database call, no credential and nothing derived from the request, so there is nothing in it to leak. It exists because the browser's sign-in prompt is browser chrome and cannot be styled or explained, and meeting it cold - then landing on raw JSON after pressing Escape - reads as a broken site rather than a private one. The app moved to `/app`, which is gated along with `/assets/*` and every `/api/*` route. `/healthz` and `/readyz` are also above the gate: A platform health check cannot authenticate, and a gated one gets the service marked unhealthy and killed. Neither leaks anything: one answers `{ok:true}`, the other `{ok, db:'up'\|'down'}`. Every `/api/*` route is behind the gate, including all nineteen write routes. |
| 2.3 | Credentials are environment variables set in the host's settings panel, not in source and not in the repository | **Yes** | There is no shared password any more — each person has their own account, and the server holds only `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, both read from `process.env` and set in Render's panel. `server/.env.example` carries placeholders. The service role key bypasses RLS, so it is server-only and never in a `VITE_` variable: everything prefixed `VITE_` is compiled into a file anyone can download. |
| 2.4 | The marker can open the app | **Yes** | A marker account is created like any other — sign up with an email address on the live site. The address and password for one are in the **private** workspace `project/README.md`, alongside the live URL. Never in the public repository. |
| 2.5 | Supabase Row Level Security | **Yes — on for every table** | Verified, not assumed. All seven tables have `rowsecurity = true` with policies: `organizations`, `memberships`, `potf_templates`, `readings_overrides`, `settings`, `scheduled_masses`, `readings_cache`. Isolation was tested both directions with two parishes and two users — one parish's user sees only its own prayers, settings and org, and an attempt to **write** a row into the other parish was rejected by the policy's `WITH CHECK`. `readings_cache` is deliberately shared and read-only to clients: scripture for a date is the same fact for every parish, and only the server (service role) writes it, so a browser cannot poison it. Supabase's own advisor was run after the migration; it flagged two `SECURITY DEFINER` helpers as callable over REST and both were revoked. |
| 2.6 | Every database query taking user input uses parameters, never string concatenation | **Yes** | Every one of the twenty query call sites binds its values with `?` or `@named`. The one exception was `routes/settings.js`, which assembled its `WHERE` clause by joining strings — always with bound values and behind `isIsoDate()` validation, so never injectable, but the wrong shape. **Fixed on 27 September:** replaced with four fixed query constants chosen by which bounds are present, so no SQL is built at run time at all. Verified against `?from=DROP TABLE` and a malformed `to=`. |
| 2.7 | Error responses do not print stack traces or connection details to the browser | **Yes** | The error handler in `src/app.js` returns `'Something went wrong on the server.'` for any 5xx when `NODE_ENV=production`, and logs the detail server-side. 4xx errors return their own message, which is written for the user and names no internals. `db/pool.js` exits at boot with a plain message rather than surfacing a connection error into a response. |
| 2.8 | Debug, seed or reset routes added during development are deleted | **Yes** | `grep -rniE "'/(debug\|reset\|seed\|dev\|test\|admin)" server/src/routes/` returns nothing; there were never any. Seeding is a command (`npm run seed`), not an endpoint. `DELETE /api/readings/cache` is a real user-facing feature in Settings, not a debug route, and it is behind the gate. |
| 2.9 | Rate limiting | **Yes** | `express-rate-limit` on `/api` in `src/app.js`, applied *after* the gate so a signed-in office is measured separately from anonymous traffic at the door: 600 requests a minute, which is generous because opening a month fires one calendar request plus one check per chosen day and a 200-day batch polls its own progress. It is a brake on abuse, not a quota. Disabled under `NODE_ENV=test` so the suite is not throttled. Sign-in attempts are rate-limited by Supabase, not here. |
| 2.10 | `helmet` | **Yes** | In `src/app.js`, with a Content-Security-Policy written to fit rather than switched off. `styleSrc` allows `'unsafe-inline'` because the built client needs it; `scriptSrc` does **not**, which is why the landing page's fragment forwarder is a file at `/auth-forward.js` and not an inline block. `connectSources()` derives `connect-src` from `SUPABASE_URL` instead of hardcoding it or leaving it open, and `server/test/csp.test.js` exists because getting that wrong caused a real outage: the browser blocked every sign-in request before it left the page, `fetch` rejected with "Failed to fetch", and nothing was logged anywhere. A policy that is too tight fails silently in the browser with no server-side trace, so it gets a test. |

## 4. Copyright — the risk that is actually specific to this project

Not on the announcement's list, but it is the thing most likely to go wrong here and it belongs in an honest checklist.

| # | Item | Answer | Evidence |
| - | --- | --- | --- |
| 4.1 | The office's transcribed prayers stay out of the repository | **Yes** | The General Intercessions volumes (ST PAULS Philippines) are published, copyrighted books. The transcriptions live in `server/data/orillo/`, git-ignored, and the public installer is built without them. A fresh clone runs on placeholder prayers and reports which sections it could not find. |
| 4.2 | Scripture text is not redistributed | **Yes, after a near miss** | The readings are the New American Bible, copyright USCCB and the Confraternity of Christian Doctrine. They are fetched at runtime and cached on the user's own machine, never committed. The first version of `server/tools/build-demo-seed.mjs` serialised whatever `buildDay()` returned straight into the committed `client/src/api/seed.json`, which would have published the full reading text **and**, on my machine, the office's transcriptions. It now replaces every body of text with one stand-in line and ships citations only. Checked with `grep -c "not included in the demo"` (24) and a `grep` for distinctive phrases from the readings (0). |
| 4.3 | The printed ORDO and the scans are not committed | **Yes** | `Needed info/` is git-ignored, along with `server/data/orillo/`. |

Verified live against https://liturgygen.onrender.com: `/` with no header returns 401 with `WWW-Authenticate: Basic realm="LiturgyGen"`, the configured credential returns 200, a wrong password returns 401, and `/healthz` and `/readyz` answer unauthenticated as intended.
3. ~~**Put the credentials in the private workspace `project/README.md`**~~ — **done, 4 October 2026**, in this folder's `README.md`, which is git-ignored along with the rest of `Docu/`. Still outstanding: **open the URL in a private window** as the marker would, and **reset the database password in the Supabase dashboard**, which was pasted into a chat transcript during deployment. Also outstanding, and cheap: **turn on leaked-password protection** in Authentication - Policies, which Supabase's own advisor flags as off.

Worth being clear about the order of risk. The repository being public is not itself a problem: no secret has ever been committed, and the audit above is what says so. The problem would be a **deployed** app with nineteen open write routes on a public URL. As of 4 October 2026 the app **is** deployed, and the gate in front of those routes is verified working - which is what makes that acceptable rather than reckless.

**The riskiest thing about this project** is not injection or credentials. The secrets are a connection string and a Supabase service role key, neither of which has ever been committed and both of which live only in the host's settings panel. It is that the app's entire value comes from text somebody else owns — two published books of intercessions and the New American Bible — and that a public repository redistributing either would be a real problem with my name permanently attached. The first draft of the demo seed generator would have done exactly that. What I did about it: the books never enter version control, the scripture is fetched at runtime and stripped out of anything committed, and the public installer ships without the office's data. What I knowingly accepted: a gmail address left in eighteen historical commits, and one Supabase advisory left standing — `public.user_org_ids()` is a `SECURITY DEFINER` function the `authenticated` role can call over RPC. Its whole body is `select org_id from memberships where user_id = auth.uid()`, so a caller can only ever read back their own parish ids, which they already know; it is `SECURITY DEFINER` precisely so the memberships policy does not recurse into itself. Moving it to a schema PostgREST does not expose is the clean fix and rewrites every policy that calls it, so it is named here rather than done the week of the recording.
